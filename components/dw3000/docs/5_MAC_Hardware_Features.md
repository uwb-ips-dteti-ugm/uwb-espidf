## 5.1 MAC Level Processing in the DW3000

The DW3000 offloads selected MAC-level operations from the host processor to reduce unnecessary interrupts and improve system throughput.

### Transmit side

- Transmits data from `TX_BUFFER` with frame length as specified by `TXFLEN` in `TX_FCTRL`
- Automatically appends the **2-octet FCS** (CRC) as the last two bytes of the payload
- Performs **no other MAC TX processing** — the host must prepare a correctly formatted IEEE 802.15.4 frame

### Receive side

- Validates the FCS of every received frame
- Can parse IEEE 802.15.4 frames to match destination address against the IC's own addresses (frame filtering, see §5.4)
- Can automatically send an **Imm-Ack** in response to Data or MAC command frames with the ACK request bit set (see §5.5)
- Delivers the received frame in **`RX_BUFFER_0`**; frame length is reported in the `RXFLEN` field of `RX_FINFO`
- Performs no additional MAC-level receive processing — the host parses the frame according to IEEE 802.15.4

> **Note:** Auto-ACK only applies to the **immediate acknowledgement (Imm-Ack)** for frames with Frame Version 0b00 or 0b01. Enhanced Ack (Enh-Ack, frame version 0b02) must be generated by the host.

## 5.2 General MAC Message Format

The MAC message occupies the **PHY Payload** portion of the UWB packet.

- Standard frame: up to **127 octets**
- Extended frame mode (§3.4): up to **1023 octets**

```
┌──────────────────────────────────────────────────────────────────┐
│                          PHY Payload                             │
├──────────────────────────────────────────────────────┬───────────┤
│                    MAC Header (MHR)                  │MAC Footer │
├────────┬────────┬──────────┬──────────┬──────┬───────┤  (MFR)   │
│ Frame  │  Seq   │  Dest    │  Dest    │ Src  │  Src  ├──────────-┤
│Control │Number  │  PAN ID  │ Address  │PAN ID│Address│   FCS    │
│2 octets│1 octet │0 or 2 B  │0,2,or 8 B│0or2B │0,2,8 B│ 2 octets │
│        │        │          │          │      │       │          │
│        │        │     + Aux Security Header           │          │
│        │        │     0, 5, 6, 10, or 14 octets       │          │
└────────┴────────┴──────────┴──────────┴──────┴───────┴──────────┘
                                          ↕
                               Variable MAC Payload
```

The MAC header is parsed by the DW3000 during frame filtering to match the destination address against:
- **EUI_64** (Sub-register 0x00:04 — Extended Unique Identifier)
- **PAN ID + Short Address** (Sub-register 0x00:0C — PANADR)

## 5.3 Cyclic Redundancy Check

The DW3000 includes hardware CRC generation and checking for the **16-bit FCS**.

- **TX**: FCS is automatically calculated and appended to every transmitted frame
- **RX**: FCS is recalculated over the received frame and compared with the received FCS
  - Match → `RXFCG` (Frame Check Good) set in `SYS_STATUS`
  - Mismatch → `RXFCE` (Frame Check Error) set; frame is discarded

To disable FCS transmission (e.g. when using a non-802.15.4 MAC protocol):
- Set `DIS_FCS_TX` bit in `SYS_CFG`

## 5.4 Frame Filtering

Frame filtering allows the DW3000 to accept only frames that match configured address criteria, eliminating unnecessary host interrupts.

- **Enable**: set `FFEN` bit in `SYS_CFG`
- **Configure frame types**: `FF_CFG` register — 10 filter bits:

| Bit     | Controls                                              |
| ------- | ----------------------------------------------------- |
| `FFAB`  | Allow Beacon frames                                   |
| `FFAD`  | Allow Data frames                                     |
| `FFAA`  | Allow Acknowledgement frames                          |
| `FFAM`  | Allow MAC command frames                              |
| `FFAR`  | Allow Reserved frames (FCS check only)                |
| `FFAMP` | Allow Multipurpose frames                             |
| `FFAF`  | Allow Fragment/Frak frames (FCS check only)           |
| `FFAE`  | Allow Extended frames (FCS check only)                |
| `FFBC`  | Coordinator mode (accept source-only address frames)  |
| `FFIB`  | Allow implicit broadcast (no PAN ID, no dest address) |

### Frame Type Field Values (Table 13)

| Frame Control bits [2:0] | Frame Type        |
| ------------------------ | ----------------- |
| 0, 0, 0                  | Beacon            |
| 0, 0, 1                  | Data              |
| 0, 1, 0                  | Acknowledgement   |
| 0, 1, 1                  | MAC command       |
| 1, 0, 0                  | Reserved          |
| 1, 0, 1                  | Multipurpose      |
| 1, 1, 0                  | Fragment or Frak  |
| 1, 1, 1                  | Extended          |

### 5.4.1 Frame Filtering Rules

When frame filtering is enabled, a frame is accepted only if **all** of the following are true:

1. **Frame type** is allowed by the corresponding `FF_CFG` bit (FFAB/FFAD/FFAA/FFAM/FFAR/FFAMP/FFAF/FFAE)

2. **Frame version** must be `0x00`, `0x01`, or `0x02`

3. **Destination PAN ID** (if present) must be:
   - Broadcast PAN ID `0xFFFF`, **or**
   - Match the `PAN_ID` programmed in `PANADR` register

4. **Destination Address** (if present) must be:
   - Short (16-bit) broadcast `0xFFFF`, **or**
   - Short (16-bit) address matching `SHORTADDR` in `PANADR`, **or**
   - Long (64-bit) address matching `EUI_64`
   - > **Note:** Long (64-bit) broadcast addresses are **not supported**

5. **Beacon frames**: Source PAN ID must match `PANADR` or be `0xFFFF`

6. **Source-address-only frames** (Data/MAC command with source address but no destination): only accepted if `FFBC` is set (coordinator mode) **and** Source PAN ID matches `PANADR`

7. **No destination PAN ID and no destination address**: treated as broadcast only if `FFIB` is set (implicit broadcast mode)

8. **FCS must be correct**

### 5.4.2 Frame Filtering Notes

- The Security Enabled field in Frame Control is **not checked** — the host must decode and validate security information
- Frame rejection is reported via `AFFREJ` bit in `SYS_STATUS`; reception is aborted immediately after address field parsing
- All frame filtering configuration is in the `FF_CFG` register
- When `FFAA` is set, **all** ACK frames are accepted — the DW3000 does not distinguish Imm-Ack from Enh-Ack; the host must identify Enh-Ack by parsing the received frame
- Enhanced beacon frames are accepted even if the beacon's Source PAN ID does not match
- **Multipurpose frames**: DW3000 does not correctly check the Frame Version field — host software must validate the version of any received Multipurpose frames

> **Warning:** Prolonged receiver-on with frame filtering is power-hungry. This mode is best used only with mains-powered equipment.

## 5.5 Automatic Acknowledgement

The DW3000 can automatically transmit an **immediate acknowledgement (Imm-Ack)** frame as defined by IEEE 802.15.4, removing the need for host intervention in the ACK cycle.

### Prerequisites for Auto-ACK

All of the following must be true:

- Frame filtering is enabled (`FFEN` in `SYS_CFG`)
- Received frame is a **Data frame or MAC command frame**
- Frame is correctly addressed to this device (passes frame filtering)
- Frame Version field is **0b00 or 0b01**
- The **ACK Request (AR) bit** in the frame control field is set
- `AUTO_ACK` configuration bit is set in `SYS_CFG`

When all conditions are met, the DW3000 automatically transitions to TX at the end of reception and transmits a **5-octet Imm-Ack** frame.

> **Note:** Enh-Ack (frame version 0b02) is **not automatically generated**. The host is responsible for generating, securing, and transmitting Enh-Ack frames.

### 5.5.1 Automatic ACK Turnaround Time

IEEE 802.15.4 specifies **12 ± 0.5 symbols** turnaround time for ACK transmission.

- Configurable via `ACK_TIM` parameter in `ACK_RESP_T` register (Sub-register 0x01:08)
- CIA analysis delays ACK response; to accelerate ACK:
  - Set `FAST_AAT` bit — moves the AAT status event earlier (see §5.5.3)
  - Or disable CIA entirely: clear both `CIA_IPATOV` and `CIA_STS` bits in `SYS_CFG` (Sub-register 0x00:10)

### 5.5.2 Frame Pending Bit

The DW3000 automatically sets the **Frame Pending bit** in auto-generated ACK frames when:

- The received frame is a **Data Request MAC command frame**, AND one of:
  - The sender's **16-bit address** matches one of four stored addresses in `LE_PEND_01` or `LE_PEND_23` registers, **and** the corresponding `LE0_PEND`–`LE3_PEND` bits in `FF_CFG` are set
  - The sender uses a **16-bit address** and `SSADRAPE` bit is set
  - The sender uses a **64-bit address** and `LSADRAPE` bit is set
- Security bit is **not set** in Frame Control, and frame version is 0 or 1

### 5.5.3 Host Notification

The `AAT` bit in `SYS_STATUS` indicates that an acknowledgement has been requested:

| `FAST_AAT` bit | `AAT` set when       |
| -------------- | -------------------- |
| Disabled (0)   | Same time as `RXFCG` |
| Enabled (1)    | Same time as `RXFR`  |

When the host detects `AAT` set during RX interrupt processing:
- Do **not** take any RX-complete action yet
- Wait for the `TXFRS` (Transmit Frame Sent) event, which signals the ACK has been sent

> **Note:** If auto-acknowledgement is not enabled, the `AAT` bit should be **ignored**.

## 5.6 Transmit and Automatically Wait for Response

The DW3000 can **automatically re-enable its receiver** after a transmission, to receive the response frame without host intervention between TX and RX.

This uses the TX-and-Wait-for-Response (W4R) fast commands:

| Command       | Description                                        |
| ------------- | -------------------------------------------------- |
| `TXW4R`       | TX, then immediately enable RX                     |
| `TXW4RCCA`    | CCA check, then TX, then RX                        |
| `TXW4RDLY`    | TX, then delayed RX (using DX_TIME)                |
| `TXW4RDLYREF` | TX, then delayed RX (using DREF_TIME + DX_TIME)    |
| `TXW4RDLYTS`  | TX, then RX after TX timestamp-relative delay      |
| `TXW4RDLYRS`  | TX, then RX after RX timestamp-relative delay      |

The delay between TX end and RX enable is controlled by the `W4R_TIM` parameter in Sub-register `0x01:08` (Acknowledgement time and response time).

> **Note:** If the received response is a correctly addressed Data/MAC command frame with ACK request set, and frame filtering + auto-ACK are both enabled, the DW3000 will transmit the ACK **before** returning to `IDLE_PLL`.

## 5.7 Pseudo Clear Channel Assessment (CCA) Mechanism

For Wireless Sensor Networks using CSMA/CA-style MAC protocols, the DW3000 provides a **pseudo CCA** mechanism to reduce packet collisions.

### Operation

1. Issue `CMD_CCA_TX` fast command
2. DW3000 enables RX and samples the air for preamble for the duration configured by `PRE_TOC`
3. **No preamble detected** → channel is clear → packet is transmitted → `TXFRS` event raised
4. **Preamble detected** → channel is busy → `CCA_FAIL` event raised → host should defer TX for a random backoff period, then retry

During the backoff period, the DW3000 returns to `IDLE_PLL` and **does not receive the detected packet**.

> **Note:** The CCA mechanism only detects preamble — it cannot detect PHR or data phases of an ongoing packet. The `RXPTO` event is **not** raised when CCA finds a clear channel.

> **Caution:** CCA consumes extra energy before every TX. In many scenarios, a simple aloha approach (transmit immediately) may be more energy-efficient. Careful analysis and experimentation are recommended.

## 5.8 Data Confidentiality and Authenticity

IEEE 802.15.4 security services supported: **data confidentiality**, **data authenticity**, and **replay protection**.

The DW3000 includes a dedicated **AES-DMA engine** capable of:
- **AES CCM\*** (128-bit key)
- **AES GCM** (128, 192, or 256-bit key)

### AES Engine Buffer Architecture

```
  Source (data to encrypt/decrypt)         Destination (result)
  ┌─────────────────┐                      ┌─────────────────┐
  │  Scratch RAM    │ 128 B                 │  Scratch RAM    │ 128 B
  │  RX buffer 0   │ 1024 B                │  RX buffer 0   │ 1024 B
  │  RX buffer 1   │ 1024 B  --> AES -->   │  RX buffer 1   │ 1024 B
  │  TX buffer      │ 1024 B                │  TX buffer      │ 1024 B
  └─────────────────┘                      │  STS KEY reg    │ 128 B
                                            └─────────────────┘

  Key sources:
  AES KEY reg (128-bit)
  AES KEY OTP (128 / 192 / 256-bit)
  AES KEY RAM (128 / 192 / 256-bit)
```

The AES engine can also **decrypt an encrypted `STS_KEY`** (received over SPI into scratch RAM) directly into the `STS_KEY` register — allowing secure key distribution without the plaintext STS key ever appearing on the SPI bus.

### 5.8.1 AES Configuration

Before running encryption or decryption, configure:

| Parameter              | Options                                       |
| ---------------------- | --------------------------------------------- |
| MIC size (`TAG_SIZE`)  | 0, 4, 6, 8, 10, 12, 14, or 16 bytes          |
| KEY size               | 128, 192, or 256-bit                          |
| KEY location           | DW3000 register, OTP, or AES KEY RAM         |
| Operation              | Encryption or Decryption                      |
| AES core               | GCM or CCM\*                                  |

> **Note:** If KEY from DW3000 registers or AES KEY RAM is selected, the key must first be written to `AES_KEY` register or `AES KEY RAM` location before starting the engine.

### 5.8.2 General TX Encryption Flow

1. Write IV to `AES_IV0`–`AES_IV3` registers
   - GCM: 96-bit IV
   - CCM\*: 128-bit IV
2. Specify source buffer (`SRC_PORT`) containing plaintext and destination buffer (`DST_PORT`) for ciphertext
3. Load the AES key — **for CCM\* mode: key must be reloaded before every AES operation**, even if unchanged
4. Set `AES_START` bit to begin DMA + encryption; wait for `AES_DONE` or `AES_ERR`
5. Repeat for additional data (scratch buffer: max **127 bytes** per operation)
6. Issue TX command to transmit the encrypted frame

### 5.8.3 General RX Decryption Flow

1. Write IV to `AES_IV0`–`AES_IV3`
2. Specify source buffer (`SRC_PORT`) = encrypted RX buffer; destination buffer (`DST_PORT`) = plaintext target
   - In-place decryption is supported (source and destination can be the same buffer)
3. Load AES key (CCM\*: reload required each time)
4. Set `AES_START`; wait for `AES_DONE` or `AES_ERR`
5. Read plaintext data from the destination buffer
6. Repeat for additional data (scratch buffer: max 127 bytes per operation)

### 5.8.4 Sample Use Cases

#### 5.8.4.1 Encrypt TX Data Prior to Transmission

1. Write AES KEY into `AES_KEY` register
2. Configure AES core type (CCM\* or GCM), KEY size, encryption mode, MIC size
3. Construct the nonce; set `SRC_PORT` and `DST_PORT` (e.g. TX buffer → TX buffer for in-place encryption, or scratch memory → TX buffer)
4. Run AES engine (`AES_START`); check `AES_DONE` / `AES_ERR`
5. Issue TX command to transmit the encrypted frame

#### 5.8.4.2 Decrypt RX Data After Packet Reception

1. After successful frame reception, read frame format and security header to extract nonce
2. Write AES KEY into `AES_KEY` register; configure core type, KEY size, decryption mode
3. Set `SRC_PORT` = RX buffer (encrypted), `DST_PORT` = RX buffer (in-place) or scratch
4. Run AES engine; wait for `AES_DONE` / `AES_ERR`
5. Read decrypted plaintext from output buffer

#### 5.8.4.3 Decrypt STS KEY into STS KEY Registers

Used when an external Secure Element (SE) delivers an encrypted STS key over SPI:

1. Host (SE) and DW3000 share a paired **STS KEK (Key Encryption Key)** — DW3000's copy is stored in OTP
2. SE encrypts the STS KEY with the STS KEK and writes the ciphertext over SPI into the DW3000 scratch buffer
3. Configure AES engine: source = scratch buffer, destination = `STS_KEY` register
4. Run AES; device decrypts ciphertext and writes plaintext STS KEY directly into `STS_KEY` register
5. STS KEY is now ready for use — it was never exposed as plaintext on the SPI bus

### 5.8.5 Note on STS KEY Decryption and Endianness

The AES-DMA engine endianness is configurable via `DMA_CFG` register (`CP_END_SEL` bit):

| `CP_END_SEL` | Endianness    | MSB of STS KEY location   |
| ------------ | ------------- | ------------------------- |
| 0            | Big endian    | Lowest address (0x02:0C)  |
| 1            | Little endian | Reversed within 32-bit words |

For STS KEY = `0xaabbcc...667788`:
- **Big endian**: address `02:0C` = `0xaa` — correct byte order, no pre-processing needed
- **Little endian without swap**: byte order is wrong — `02:0C` = `0xdd`
- **Little endian with SE byte-swap before encryption**: `02:0C` = `0x88` — correct

> **Rule for little endian:** The SE must swap the STS KEY bytes before encryption: `byte[15] = byte[0]; byte[14] = byte[1]; ...` — so that after AES decryption the correct key byte order appears in `STS_KEY`.

### 5.8.6 Note on Source and Destination Buffer Sizing

> **Critical:** Always ensure buffers are large enough for the full DMA transfer:
>
> `Header length + Payload length + MIC length < Total buffer size`

If the buffer is undersized:
- `AES_ERR` may **not be correctly flagged** by the hardware
- The internal AES block can **lock up**, requiring a **full device reset** (soft or hard) to recover
